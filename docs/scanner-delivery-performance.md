# Scanner delivery performance

The initial optimization preserves the scanner universe, eligibility screens, completed-bar rules, regressions and historical evidence. Recent pre-change jobs took 104–122 seconds from workflow creation to completion; two inspected jobs spent 35–43 seconds checking out the repository, 37–39 seconds scanning and validating, and 16 seconds committing and pushing data. These are observed samples, not a guaranteed runtime.

The scheduled workflow starts with code and top-level current data JSON in a sparse partial checkout. Before running tests or archival code, prepare_scan_checkout.py materializes every complete scan archive day referenced by scan-history.json, plus the current Eastern date. Historical days referenced only by option-observations.json materialize their complete merged option-observations.json.gz file. Whole scan days are required for daily index rebuilds; observation-only days do not need the unrelated scan archives or indexes. Both include records already rolled out of the current files. Malformed input or a failed Git fetch stops the job before archive writes. Other archive days remain tracked in Git and are not deleted or reconstructed. A sparse-worktree integration test verifies that publication retains their original tree entries.

Archive updates no longer rebuild unchanged brokerage indexes twice or rewrite unchanged compressed observations. Newly archived scans still rebuild their complete daily index; later markouts still update existing observations and preserve rolled-off events. Every pipeline stage records monotonic duration in scan-health.json alongside total pipeline time. Existing collection/provider clocks are unchanged.

Publication still commits and pushes validated data atomically using the existing workflow. This first release reduces archive work within the existing process; it does not claim to eliminate GitHub runner queues or the raw-content distribution step. Post-release workflow checkout, hydration, scan and publication times must be compared separately. The regression suite remains on every scan (previously about three seconds); validation has not been traded for speed.

The first live run of the broad day-based checkout took 6 seconds for code/current JSON, 28 seconds for archive hydration, 40 seconds for the pipeline and 14 seconds for publication. It succeeded, but did not establish a substantial overall speedup. It revealed 15 observation days were pulling unrelated scan indexes. The refined record-type selection removes those unnecessary archives; new production timing is required before quantifying that gain.
